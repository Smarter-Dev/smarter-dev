# Rendering fenced LaTeX in chatbot replies

Assessed 2026-07-29 against:

- `alvesvaren/latex-bot-ts` at commit
  [`18cd37b`](https://github.com/alvesvaren/latex-bot-ts/tree/18cd37ba9abbc52fe174a419585105765adb2594)
- this repository at commit `6ac6c4f`

## Scope

This feature applies only to normal chatbot replies. There is no `/latex`
command and no attempt to recognize `$...$`, `$$...$$`, or other math syntax.

The chatbot writes each equation in a fenced block:

````markdown
Some response foobar

```latex
E = mc^2
```

Some conclusion foobar
````

The bot sends:

1. `Some response foobar` as a text message.
2. The rendered `E = mc^2` as an image message.
3. `Some conclusion foobar` as a text message.

That is a small, well-contained change. The chat integration itself is about
**1–2 engineering days**. Adding and production-hardening the renderer is
another **1–2 days**, so the complete feature is approximately **2–4 days**.

## Implementation

### 1. Tell both answer-producing agents to use the fence

This repository has two paths that can write the final reply, so add the same
instruction to:

- `smarter_dev/bot/agents/prompts/chat_agent.md`
- `smarter_dev/bot/agents/prompts/writer_agent.md`

Suggested instruction:

````text
When an answer needs mathematical notation, put each complete equation in its
own fenced block whose language is exactly `latex`:

```latex
E = mc^2
```

Put explanations outside the fence. Do not use inline LaTeX delimiters. Use
ordinary Markdown code fences for source code.
````

Updating both prompts matters because configured channels can use either the
single-stage chat agent or the two-stage writer.

### 2. Split the returned message into ordered sections

Add a small pure helper, for example
`smarter_dev/bot/agents/latex_blocks.py`:

```python
@dataclass(frozen=True)
class TextSection:
    text: str


@dataclass(frozen=True)
class LatexSection:
    source: str
    original: str


def split_latex_sections(message: str) -> list[TextSection | LatexSection]:
    ...
```

A short line-oriented parser is preferable to a broad regular expression. It
only needs two states: outside a fence and inside a `latex` fence. It should:

- preserve section order;
- ignore all non-`latex` code fences;
- treat an unclosed fence as normal text;
- skip empty text sections;
- retain the original fence as a failure fallback.

For the example above it returns:

```python
[
    TextSection("Some response foobar"),
    LatexSection(source="E = mc^2", original="```latex\nE = mc^2\n```"),
    TextSection("Some conclusion foobar"),
]
```

### 3. Render each LaTeX section

The referenced bot's render path is only in
[`commands/latex.ts`](https://github.com/alvesvaren/latex-bot-ts/blob/18cd37ba9abbc52fe174a419585105765adb2594/commands/latex.ts):

1. MathJax converts TeX to SVG.
2. Sharp converts the SVG to PNG.
3. The PNG is uploaded to Discord.

Reuse that design behind a Python-facing service:

```python
class LatexRenderer(Protocol):
    async def render(self, source: str) -> bytes:
        ...
```

The current bot image is Python-only, so MathJax can run either as a tiny
internal Node service or as one long-lived Node worker in `Dockerfile.bot`.
Initialize it once; do not start Node separately for every equation.

The renderer should impose basic limits: maximum source length, render timeout,
maximum image dimensions/bytes, and a small concurrency cap. Load MathJax's
[`ui/safe` extension](https://docs.mathjax.org/en/latest/options/safe.html)
because the model may repeat math supplied by Discord users.

### 4. Send the sections sequentially

Add a fenced-response branch in
`smarter_dev/bot/services/chat_engine.py`. The existing `_send_text()` method
cannot be used for the whole reply because it attaches images only at the end.

The new path is conceptually:

```python
sections = split_latex_sections(body.message)

for section in sections:
    if isinstance(section, TextSection):
        await send_text(section.text)
    else:
        png = await latex_renderer.render(section.source)
        await send_image(png)
```

Use the existing `hikari.Bytes` attachment pattern. Apply `reply_to` only to the
first Discord message in the sequence. If a render or image upload fails, send
`LatexSection.original` as text in that same position so the answer remains
complete.

Parse the response before the current overlong-response rewrite. Otherwise the
rewriter may change an equation or remove a fence. Text sections can still be
split to Discord's 2,000-character limit individually; LaTeX source must pass to
the renderer unchanged.

Images generated by the agent's existing `generate_image` tool are unrelated to
the fenced sequence and can continue to be attached after the final section.

## Tests

Add focused tests for:

- no fence: the existing send path is unchanged;
- one fence: sends `text → image → text`;
- several fences: preserves exact order;
- a normal code fence: remains text;
- unclosed `latex` fence: remains text;
- render failure: sends the original fence between the surrounding messages;
- missing `Attach Files`: sends the original fence instead of losing content;
- two renders completing out of order: messages are still sent in source order;
- the Discord reply anchor appears only on the first sent section;
- both final-answer prompts contain the `latex` fence instruction.
