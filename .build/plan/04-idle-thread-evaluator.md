# Stage 04 — The idle evaluator: DeepSeek V4 Flash decides after a long gap

**Stable id:** `idle-thread-evaluator`

## Outcome

When someone leaves a Quick chat alone for longer than fifteen minutes and then
sends a message, a cheap evaluator model reads the tail of the current thread and
the new message and answers one question: is this the same subject, or a new one?
If it is a new one, a thread boundary is drawn **before** the expensive chat model
is called, so the chat model never loads the old subject at all.

That ordering is the point. The stage 03 tool can only fire after the agent has
already been handed the old thread; this one fires before, which is where the
saving lives.

The evaluator is DeepSeek V4 Flash. The person choosing their chat model has no
say over it and never sees it — it is an administrator setting, like the web
summarizer and the compaction model already are.

This completes the feature.

## Assumptions

On the review thread, may come back corrected:

- **Fifteen minutes is an administrator setting defaulting to 15**, not a
  constant, because it will want tuning against real behaviour.
- **The evaluator fails open.** If the model errors, times out, or is
  unconfigured, the message is treated as a continuation and the turn proceeds.
  A classifier must never be able to block someone's reply.
- **The evaluator is DeepSeek V4 Flash by default but administrator-changeable**,
  with an optional fallback, matching how every other auxiliary model on the Chat
  settings page works.

### 2. `smarter_dev/web/chat/thread_evaluator.py`

A new module. Keep it small and keep the model call injectable so it is testable
without hitting a provider.

```python
class ThreadVerdict(BaseModel):
    """Whether an incoming message belongs to the thread already in progress."""

    continues_current_thread: bool = Field(
        description="True when the message follows on from the conversation so far."
    )
    reason: str = Field(description="One sentence naming the subject you judged it against.")
```

A system prompt that states the bar plainly and biases toward continuation, since
a wrongly drawn line costs someone context they wanted kept, while a wrongly kept
thread costs only tokens. Say that asymmetry out loud in the prompt. Tell it the
gap length, since "they came back after four hours" is real evidence and "after
sixteen minutes" is barely any.

The user prompt carries: how long the gap was, the tail of the current thread
(cap it — the last three exchanges, each message truncated to around 400
characters, is plenty for a topic judgement and keeps this genuinely cheap), and
the incoming message. Label the conversation content as untrusted data that must
not be followed as instructions, the way `BASE_PROMPT` in `subagents.py` does —
this is a model reading user-authored text and it should not be steerable by it.

The entry point:

```python
async def classify_incoming_message(
    *,
    settings: ChatSettings,
    conversation: WebChatConversation,
    turn: WebChatTurn,
    owner_id: UUID,
    gap: timedelta,
    recent_messages: list[WebChatMessage],
    incoming: str,
    agent=None,
) -> ThreadVerdict | None
```

Returns `None` on any failure — that is the fail-open signal, and the caller reads
`None` as "continuation". Log a warning with the exception when it happens; do
not swallow it silently.

Build the agent from the catalog through `build_model_for` / `model_settings_for`
(`smarter_dev/shared/model_router.py`), wrapped in `SpendMeteredModel` with a
`MeteringContext` carrying `operation_type="thread_evaluator"` and
`operation_prefix=f"chat:{turn.id}:thread_eval"`, so the spend lands on the
dashboard next to the summarizer and compaction rows.

Reasoning: ask for `ReasoningLevel.NONE` and let `resolve_reasoning_level` clamp
it to the lowest rung DeepSeek offers. This is a one-bit judgement; do not pay for
thinking.

Try the configured model, then the fallback if one is set — the same
try-then-fallback shape as `_run_aux_with_fallback` at `jobs.py:765-795`. If you
can reuse that function by generalising its output type rather than duplicating
the loop, prefer that; it also re-reads the settings row so an administrator's
change applies at the next operation rather than the next turn, which is
behaviour worth keeping. If generalising it turns messy, write the small loop
here and leave a comment saying why.

### 3. Hook it into the turn

In `run_chat_turn` (`jobs.py:2350`), between `_preflight` (2361) and
`_structured_history` (2386).

Run the evaluator only when **all** of these hold:

- `conversation.chat_mode == "quick"`.
- The turn is a fresh message, not a regeneration — `turn.kind != "regenerate"`
  and `turn.regenerates_turn_id is None`. Regenerating an old reply must never
  move a boundary; that would silently rewrite what the model can see for a turn
  the person is only asking to redo.
- The current thread already has at least one prior exchange. Reuse the same
  emptiness test stage 03 used for tool availability so the two rules cannot
  drift.
- The gap exceeds `settings.thread_idle_minutes`. Measure from the `created_at` of
  the newest message in the current thread to this turn's `created_at`. Use the
  turn's own timestamp rather than `datetime.now(UTC)` — a turn sitting in the
  queue behind a backlog must not be judged idle because the worker was slow.

When the verdict is `continues_current_thread == False`, call `open_thread(...)`
with `start_sequence = turn.response_sequence - 1`, `origin="evaluator"`,
`reason=verdict.reason`, and the title from `derive_thread_title(user_message.content)`.
Publish `chat_thread_started` and mirror it through `_event`, exactly as stage 03's
tool does — factor that publish into one function both call rather than writing it
twice.

Because this runs before `_structured_history`, the flooring from stage 01 does
the rest with no further change.

**Idempotency.** `run_chat_turn` is retried — up to five attempts, per the handler
decorator. A retry must not run the evaluator again and must not open a second
thread. `open_thread` already returns `None` when a thread starts at that
sequence, which covers the second half. For the first half, check for an existing
thread at `turn.response_sequence - 1` before spending anything on a model call,
and skip straight past if one is there. Do that check first, before the gap
arithmetic.

### 4. Sequencing against the agent's tool

Both mechanisms can want to act on the same turn. If the evaluator has already
drawn the line, the agent's `start_new_thread` tool must not be registered for
that turn — after the boundary the history is empty, so the `bool(history)` test
stage 03 uses already handles this. Confirm it rather than assuming it: the
evaluator runs before `_structured_history`, so `history` really is computed after
the boundary exists. Add a test that pins the ordering.

## Tests (write these first)

New `tests/web/thread_evaluator_test.py`, with the model call stubbed via the
`agent=` injection point (the pattern in `tests/web/chat_memory_dream_test.py:71-96`
— a small stub class with an `async def run(...)` returning an object with an
`.output`).

Settings:
- `ensure_settings` seeds `thread_evaluator_model_key='deepseek-v4'` and
  `thread_idle_minutes=15` on a fresh database.
- `validate_settings_input` rejects an unknown evaluator key, an evaluator model
  without pricing, and `thread_idle_minutes` of 0 or negative.
- A valid form round-trips through the admin POST handler.

Gate logic — assert the model is **not** called at all in each of these:
- a standard conversation, whatever the gap;
- a gap under the threshold;
- a regeneration turn, even with a long gap;
- a Quick chat whose current thread has no prior exchanges;
- a turn that already has a thread at its start sequence (the retry case).

Verdicts:
- `continues_current_thread=False` opens a thread with `origin='evaluator'` at
  `turn.response_sequence - 1`, carrying the model's reason.
- `continues_current_thread=True` opens nothing.
- A stub that raises returns `None` from `classify_incoming_message`, opens
  nothing, and the turn proceeds — the fail-open guarantee. Test the same for a
  model key that does not resolve.

End to end:
- After an evaluator-drawn boundary, `_structured_history` for that same turn
  returns an empty history, and `start_new_thread` is consequently not registered.
- The prompt sent to the stub contains the incoming message and the gap, and does
  **not** contain messages from before the current thread's `start_sequence`.

Run `uv run pytest`. Compare the failure set against a clean tree — several
failures are pre-existing (listed in stage 01).

## Acceptance criteria

- The Chat settings admin page offers a thread evaluator model, a fallback, and an
  idle threshold, defaulting to DeepSeek V4 Flash and 15 minutes, and refuses an
  unpriced model.
- In a Quick chat, a message sent after the threshold with a genuinely new subject
  produces a boundary before the chat model runs, and the chat model's history for
  that turn is empty.
- A message sent after the threshold on the same subject produces no boundary.
- An evaluator failure never fails, delays past a timeout, or blocks a turn.
- Evaluator spend appears as `operation_type='thread_evaluator'` rows and is
  visible on the usage dashboard.
- No standard conversation ever calls the evaluator.
- `uv run pytest` shows no new failures; `semgrep` and `gitleaks` clean.

## Notes

- Deployment: no new secret and no new environment variable —
  `OPENCODE_ZEN_API_KEY` already serves DeepSeek and is already in the cluster.
  The migration runs through the existing `k8s/migrate-job.yaml`
  (`scripts/migrate.py --only main`) before the rollout, as usual.
- Worth watching for the first week after this ships: how often the evaluator
  actually fires, and its continuation-vs-new split. If it almost never draws a
  line, the threshold is too high or the prompt is too conservative; if people
  complain the agent forgot something, it is too eager. That ratio is the one
  number that tells you which.
- A reasonable follow-up, deliberately not in scope: let the evaluator's decision
  be undone from the divider ("actually, this is the same thread"). It needs a
  product decision about what undoing does to a turn that has already run.
